# confdb / 1confdb-knw — подробная документация

Подробности проекта: база из выгрузки конфигурации в файлы, проверка
СКД-запросов, инструменты MCP-сервера (базы, группы, сетевой режим),
опции извлечения, бенчмарк, схема базы данных по колонкам и состав
модулей. Краткое описание, установка и быстрый старт — в
[README.md](../README.md).

## Извлечение: подробности

По умолчанию любая ошибка декодирования объекта прерывает извлечение.
Флаг `--skip-errors` (в консольном интерфейсе — опция 6 «Пропускать
ошибки объектов») пропускает сбойные объекты и продолжает разбор:
каждый пропуск печатается с внутренней причиной, в конце — итоговое
число. Дамп и база при этом неполные (пропущенные объекты и их
подобъекты отсутствуют) — режим для больших конфигураций, где единичный
сбойный объект не должен блокировать всю выгрузку.

Повторное извлечение одного и того же файла отсекается до распаковки: `extract`
считает SHA-256 исходного `.cf/.cfe/.epf` (885 МБ — 1,7 с) и сравнивает его
с отпечатком в таблице `source` целевой базы. Совпало — база уже содержит ровно
эту конфигурацию, извлечение не запускается (код возврата 0), а сообщение
называет отпечаток и дату сборки; `--force` пересобирает принудительно. Если
база собрана из другого файла, печатается предупреждение о перезаписи. Сам
отпечаток и размер исходника видны в `configuration_info` (полностью) и в
`db_list` (первые 16 символов) — по ним две базы сравниваются на происхождение
без повторной выгрузки. В консольном интерфейсе вместо `--force` задаётся
вопрос «Пересобрать базу всё равно?».

## База из выгрузки конфигурации в файлы

`confdb extract <каталог>` принимает не только `.cf`, но и каталог
иерархической выгрузки конфигуратора («Выгрузка конфигурации в файлы»,
признак — `ConfigDumpInfo.xml` в корне). Такая база содержит те же таблицы
и те же значения путей/типов/`code_name`/`type_str`, что и cf-база, поэтому
все инструменты MCP-сервера, `confdb check`, сравнение баз (`compare_object`,
`config_diff`) и группы работают с обоими источниками одинаково.

Главный сценарий — **LLM (или разработчик) правит файлы выгрузки, база
догоняет инкрементально, запущенный MCP-сервер подхватывает изменения сам**:

```bat
:: полная сборка (каталог выгрузки определяется автоматически)
confdb.bat extract cf\БП_РФ --db bp.db --workers 8

:: повторный запуск extract без --force = инкрементальное обновление;
:: то же явной командой:
confdb.bat update cf\БП_РФ --db bp.db
confdb.bat update cf\БП_РФ --db bp.db --no-fts   :: без пересборки FTS-индекса
confdb.bat update cf\БП_РФ --db bp.db --fts      :: пересобрать FTS, даже если модули не менялись
```

В консольном интерфейсе (`confdb-ui.bat`, пункт 2) каталог выгрузки можно
указать вместо файла `.cf` — сборка/обновление идут тем же конвейером.

### Что извлекается из выгрузки

- **объекты метаданных всех 45 классов** (справочники, документы, регистры,
  планы, бизнес-процессы, задачи, общие модули/формы/команды/макеты/картинки,
  роли, подсистемы, XDTO-пакеты, …) с иерархией `parent_id`/`ord` и путями
  в точности как в cf-базе: `Catalog/Валюты`,
  `Catalog/Валюты/CatalogForm/ФормаСписка`,
  `DataProcessor/Х/Form/Форма` (у обработок формы — тип `Form`),
  `Catalog/Х/CatalogCommand/К`, `Catalog/Х/Template/Макет`;
- **реквизиты, измерения, ресурсы, признаки субконто, колонки журналов,
  поля табличных частей** — с типами в том же формате (`Строка(10)`, `Число`,
  `Ссылка: Catalog/Х`, составной `A | B`, `ОпределяемыйТип: DefinedType/Х
  (состав)` — состав раскрывается рекурсивно) и связями `attribute_ref`;
- **модули BSL** (`.bsl` файлы выгрузки) с разбором на методы: те же
  `code_name` (obj/mgr, корневые app/802/con/seance) и `context` общих
  модулей («Сервер,Внешнее соединение,…»);
- **значения перечислений, предопределённые элементы** (`Ext\Predefined.xml`,
  включая иерархию и коды) **и виды субконто предопределённых счетов**
  (`ExtDimensionTypes` с флагами);
- **запросы СКД** из текстовых макетов `Templates\<Имя>\Ext\Template.xml`
  (таблица `skd_query`, проверяется `confdb check`);
- **пакеты XDTO** — из того же бинарного `Ext\Package.bin`, что и в .cf
  (таблицы `xdto_*`);
- **права ролей** из текстового `Roles\<Имя>\Ext\Rights.xml`: объектные права
  (sparse: `true`→'1', `false`→'-1'), RLS-условия прав (`rls_text`) и именованные
  шаблоны RLS (`role_rls_template`); цели разрешаются по точечным именам —
  объект, реквизит/ресурс/измерение/признак субконто/реквизит адресации,
  табличная часть и её поле, форма, команда, макет, операция веб-сервиса,
  шаблон URL и метод HTTP-сервиса, вложенная подсистема, конфигурация;
- **состав подсистем** (`<Content>`), **привязки общих реквизитов**
  (`Ext\…\Content`), **состав планов обмена** (`Ext\Content.xml` — внедряется
  в `header_json` и читается `object_card`);
- **подписки на события**: событие (русское имя), обработчик (общий модуль +
  метод), источники — в `object_card` и индексе подписок MCP-сервера;
- **карта файлов выгрузки** (`file`) и их состояние (`dump_file`: размер,
  mtime, SHA-256) — основа инкрементального обновления; отпечаток всего
  состава пишется в `source.file_sha256` (манифест: SHA-256 по отсортированным
  парам «путь + хэш»).

### Инкрементальное обновление (`confdb update`)

- обход выгрузки делает только `stat` каждого файла (97 тыс. файлов — ~11 с);
  SHA-256 считается лишь у файлов с изменившимся размером/mtime, поэтому
  правка и откат назад изменением не считаются;
- **гранула обновления — объект верхнего уровня со всем деревом** (XML,
  модули, формы, команды, макеты): его строки удаляются FK-каскадом и
  вставляются заново; изменённые, добавленные и удалённые объекты
  обрабатываются единообразно;
- межобъектные связи переразрешаются глобально: `attribute_ref` — по
  `target_path`, цели прав ролей — по `target_uuid` (FK у них `ON DELETE
  SET NULL`, поэтому строки ДРУГИХ ролей и объектов переживают переустановку
  цели; `target_object_id` права на реквизит/ТЧ/подобъект — объект-владелец,
  как в cf-базе), субконто — по uuid; права ролей, ссылавшихся на переустановленные
  объекты, перечитываются из своих `Rights.xml`, даже сама роль не менялась;
  цели, которые при записи не разрешились и хранятся ИМЕНЕМ, переразрешаются
  для переустановленных гранул (цель могла появиться позже — например, когда
  новый код извлекает больше подобъектов);
- составы подсистем и общих реквизитов пересчитываются целиком (~1 с);
- FTS-индекс пересобирается автоматически, если менялись `.bsl` (и всегда —
  с `--fts`);
- замер на реальной выгрузке БП (97 170 файлов, 5.7 ГБ; база 2.6 ГБ,
  567 тыс. методов): правка одного общего модуля → обновление за **18.7 с**,
  id не затронутых объектов не меняются; обход без изменений — те же ~17 с
  и ранний выход.

### Запущенный MCP-сервер — не помеха (hot reload)

База из выгрузки создаётся в **WAL**, поэтому `update` пишет её in-place
одной транзакцией при живых read-only соединениях сервера: до COMMIT сервер
отвечает по старому снимку, после — по новому. Сервер на каждый вызов
инструмента сверяет `PRAGMA data_version` и при изменении сам сбрасывает
производные кэши (счётчики поиска, контексты запросов и BSL-семантики,
индексы подписок и uuid, FTS-манифест) — перезапуск не нужен. FTS-шарды
пишутся **поколениями** (`<база>.fts\g<N>_<k>.db` + манифест `index.json`):
пересборка не перезаписывает файлы, открытые сервером (Windows), а сервер
переключается на новое поколение при той же сверке `data_version`.

Сервер (stdio и HTTP) пишет pidfile `<база>.server.json` (pid, порт, алиас,
командная строка) и удаляет его при выходе; `update` видит живой процесс и
сообщает, что обновление пройдёт на ходу. **Остановка сервера нужна только
для ПОЛНОЙ пересборки** (`extract --force` удаляет файл базы — Windows не
позволит, пока он открыт): команда назовёт pid и попросит остановить сервер.

### Отличия dump-базы от cf-базы (на совместимость не влияют)

Паритет всего остального закреплён тестом `tests/test_parity.py`: одна
синтетическая конфигурация описывается в обоих форматах, две базы строятся и
сравниваются по таблицам (пути, типы, `type_str`, модули/методы, права,
предопределённые, СКД); осознанные отличия перечислены ниже и из сравнения
исключены.

- `meta_object.header_json` хранит исходный **XML** объекта вместо внутреннего
  JSON декодера; `header_props` читает оба формата (XML-адаптеры: свойства
  конфигурации, периодичность и режим записи регистра, группы
  измерения/ресурсы/реквизиты, пространство имён XDTO, подписки на события,
  состав плана обмена);
- `ord` — плотные индексы списков `ChildObjects` (в cf — разреженные позиции
  в бинарном заголовке); относительный порядок тот же;
- `obj_version` — в cf версия формата объекта из бинарного заголовка (`802`,
  `2`, `13`, …), в dump редакция конфигурации: `803` у детей и `803xx` у корня;
- `attribute_ref.uuid` — в cf «источниковый» uuid дескриптора типа (таблица
  `.10`), в dump uuid объекта-цели; связь в обоих базах несёт пара
  `object_id`+`target_path` (они одинаковы);
- `type_str` точнее: платформенные типы, которые бинарный декодер не
  расшифровывает (в cf — NULL), получают имена («ХранилищеЗначения»,
  «УникальныйИдентификатор», «ТаблицаЗначений», …), а ссылки не страдают от
  оверрезолва коллизий имён (в cf «Хозрасчетный» давал обе цели
  `AccountingRegister/… | ChartOfAccounts/…`, в dump — точную одну);
- `file.path` — относительные пути выгрузки (`Catalogs/Валюты.xml`);
  содержимое макетов `Template.*` не хранится (запросы СКД извлечены, а сами
  листы — мегабайты справочных данных);
- права: `role_rights_state.version='xml'`; Designer опускает в `Rights.xml`
  строки, совпадающие с умолчаниями (в т.ч. атрибутов при
  `setForAttributesByDefault`), поэтому строк меньше, чем в cf, — семантика
  sparse та же («нет строки = право не задано»); цели `StandardAttribute.*`
  (стандартные реквизиты) не извлекаются в обеих базах и хранятся именем;
- `right_uuid` — те же платформенные uuid видов прав, что в cf-базе
  (соответствие английских имён `Rights.xml` и uuid накопано по паре
  «выгрузка + cf одной конфигурации» и подтверждено RLS-якорями); для выгрузок
  другой версии платформы редкие uuid могут отличаться — тогда в `right_uuid`
  записывается само английское имя, это заметно и не ломает разрешение целей.

### Ограничения

- поддерживается иерархическая выгрузка конфигурации (format="Hierarchical");
  полные пересборки требуют остановленного MCP-сервера;
- `update` требует той же схемы базы (ревизия 9+): база из `.cf` или старая
  база будет пересобрана полностью автоматически.

## Проверка запросов СКД

`confdb check <база>` прогоняет все запросы
таблицы `skd_query` через встроенный разборщик языка запросов 1С
(`src/confdb/query_lang.py`):

- синтаксис: ПОМЕСТИТЬ/УНИЧТОЖИТЬ, ОБЪЕДИНИТЬ [ВСЕ], соединения (включая вложенные
  и перечислением), вложенные запросы, ВЫБОР/ВЫРАЗИТЬ, виртуальные таблицы
  с аргументами, параметры `&…`, необязательные области СКД `{…}`, `ДЛЯ ИЗМЕНЕНИЯ`;
- семантика по метаданным: существование таблиц (`Справочник.Х`, `РегистрНакопления.Х.Обороты`
  и т.п.), существование полей первого уровня (meta_attribute + стандартные поля +
  общие реквизиты, без учёта регистра), цепочки разыменования ссылок через
  `attribute_ref` (второй и далее уровни — мягко: составные/абстрактные типы
  не всегда раскрываются).

Код возврата 1 и список сообщений — если какой-то запрос не прошёл.

## 1confdb-knw — MCP-сервер для внешних LLM

```bat
:: сервер знаний по конфигурации 1С и BSL; stdio (JSON-RPC, read-only)
1confdb-knw out.db
:: то же через CLI: confdb 1confdb-knw out.db
:: несколько баз сразу: основная конфигурация + расширения/обработки
1confdb-knw main.db extension.db processor.db
:: несколько групп конфигураций одновременно — повтор флага добавляет базу
:: в ту же группу, а группы остаются раздельными (запрос к одной — group=<имя>)
1confdb-knw --group УНФ=unf.db --group УНФ=unf_ext.cfe.db --group БП=bp.db
:: + синтакс-помощник платформы (документация встроенного языка 1С)
1confdb-knw out.db --syntax-db hbk\syntax.db
```

Путь к базе можно не указывать: `1confdb-knw` без аргумента берёт
`last_db` из `~/.confdb/config.json`, а при его отсутствии сам ищет
`*.db`/`*.sqlite` — в текущем каталоге, `db/` и `_out/` (и в корне
установки при запуске из venv). Одна база — запускается; несколько —
сервер печатает список и просит указать путь явно. С флагом `--group`
автопоиск не срабатывает: нужные базы названы в группах. Несуществующий путь —
сразу «Файл базы не найден» (код 2), без падения на первом запросе.
Свежая установка с базой, привезённой с другого компьютера, работает
без ручной правки конфига: достаточно положить файл в `db/` рядом
с `1confdb-knw`.

41 инструмент: `find_objects`, `object_card` (паспорт объекта: реквизиты,
табличные части, модули, формы и команды, ссылки; у регистров — измерения,
ресурсы и реквизиты отдельными группами плюс периодичность и режим записи),
`object_tree`, `find_field`, `refs_of`, `role_rights` (явные права одной роли:
по строке на цель — объект, его реквизит/поле табличной части или его табличная
часть, — с текстом ограничения доступа на уровне записей и шаблонами RLS роли;
право показывается первыми знаками своего uuid, потому что имён прав в
конфигурации нет), `object_rights` (какие роли несут явные права на объект,
включая права на его реквизиты и табличные части; параметр `role` сужает ответ
до одной роли), `module_outline`, `get_method`,
`find_method_context` (окно строк вокруг нужного вызова с номерами строк
модуля и маркерами точки вставки), `method_dependencies` (что использует
метод: общие модули и их экспортные методы, метаданные, таблицы и поля
запросов, параметры; если рядом открыта основная конфигурация, её объекты и
общие модули находятся там, а не объявляются отсутствующими),
`method_result_schema` (из чего состоит возвращаемая методом таблица
значений/структура — эвристика по тексту), `find_methods` (поиск по имени,
сигнатуре и описанию, а параметр `text` — по текстам тел методов: все места
обращения к объекту с номером строки модуля, без полнотекстового `sql`),
`skd_of`, `find_skd`, `xdto_of` (состав пакета XDTO: целевое пространство
имён, импорты, типы с базовым типом, ограничениями и значениями перечислений,
свойства с обязательностью, признаком списка и формой — атрибут или элемент,
вложенные анонимные типы; параметр `type` показывает один тип),
`find_xdto` (поиск имён типов и свойств по всем пакетам XDTO базы),
`check_query` (валидатор запроса 1С), `check_syntax` (проверка синтаксиса
модуля/фрагмента кода BSL встроенным парсером — без платформы и Java;
`text=<код>` проверить фрагмент перед выдачей пользователю, либо `path`+
`code_name` проверить существующий модуль конфигурации; возвращает
диагностики `строка:колонка [код] сообщение`, пусто = синтаксис корректен;
`semantic=True` добавляет секцию семантических замечаний ERROR/WARNING/INFO:
по базе — вызовы несуществующих/не-Экспорт методов общих модулей, обращения
к несуществующим объектам метаданных (`Справочники.Х`), запросы внутри модуля
(синтаксис + таблицы/поля), клиентские вызовы серверных общих модулей;
по коду — неиспользуемые локальные переменные, `Прервать`/`Продолжить` вне
цикла, `Перейти`, устаревшие и небезопасные глобальные вызовы: динамический
код (`Вычислить`/`Выполнить`), файловая система, интернет, модальные окна,
`ЗапуститьПриложение`, `ТекущаяДата`/`Сообщить`/`Найти`),
`sql` (только
SELECT), `syntax_search` / `syntax_card` / `syntax_children` (синтакс-помощник
платформы — документация встроенного языка 1С из отдельной базы `syntax.db`,
подключается ключом `--syntax-db`; см. «Синтакс-помощник платформы»),
`compare_object` (различия одного объекта в двух базах),
`extension_diff` (что делает расширение относительно основной конфигурации),
`configuration_info` (тип загруженного файла — конфигурация `.cf`, расширение
`.cfe`, внешняя обработка `.epf`, внешний отчёт `.erf`; имя и версия, режим
совместимости, источник и дата выгрузки) и управление базами
`db_list` / `db_open` / `db_use` / `db_close` плюс управление группами
конфигураций `group_create` / `group_add_db` / `group_remove_db` /
`group_list` / `group_use` / `group_close`. Инструкции протокола
(`initialize.instructions`)
и описания инструментов содержат справочник по схеме базы, глоссарий 1С
и рекомендуемый рабочий процесс — любая модель пользуется сервером без
контекста этого проекта.

**Пагинация поиска.** `find_objects`, `find_field`, `find_methods`, `find_skd`,
`find_xdto` и `refs_of` отдают одну страницу совпадений: `limit` задаёт её
размер (1..200), `offset` — сколько совпадений того же поиска пропустить.
Последняя строка ответа сообщает итог и продолжение —
`… всего найдено 317; показано 1–20; есть ещё 297 — следующий вызов с offset=20`
(когда страница последняя — «это все результаты»). Порядок совпадений строгий,
поэтому страницы не пересекаются и не теряют строки. У `find_xdto` типы и
свойства считаются одним списком (сначала типы, потом свойства), у `refs_of`
свой итог у каждой из двух секций, а `offset` у них общий.

Синтаксис текстов модулей сервер **проверяет** встроенным парсером BSL
(`check_syntax`): блок-конструкции, препроцессор `#Если`/`#Область`, строки,
выражения — с позициями и кодами диагностик. Отдельный вариант
`1confdb-knw-lsp` (шлюз к Java BSL Language Server) больше не нужен и снят с
поддержки. Глубокий вывод типов и разрешение имён по библиотеке платформы не
выполняются — только грамматика языка; для запросов есть `check_query`, для
связей кода — `method_dependencies`. Ошибки
инструментов возвращаются с кодом категории — `BAD_ARGS`, `BAD_REQUEST`,
`DB_LOCKED`, `DB_SCHEMA`, `DB_ERROR`, `IO_ERROR`, `INTERNAL`; при занятой
базе (`SQLITE_BUSY`) вызов повторяется автоматически.

#### Несколько баз одновременно (расширения и обработки)

Сервер держит несколько баз сразу: перечислите их при запуске либо
открывайте на ходу инструментом `db_open` (без перезапуска сервера).
Каждая база получает алиас (по умолчанию — имя файла без расширения;
при совпадении — с суффиксом `_2`, `_3`…). Все инструменты по умолчанию
работают с активной базой (при запуске — первая указанная); чтобы
запросить другую базу без переключения, передайте её алиас параметром
`db` (есть у всех инструментов). Переключение активной базы — `db_use`,
список открытых баз со статистикой — `db_list`, закрытие — `db_close`.

Типовой сценарий: извлечь основную конфигурацию, расширение и обработку
в отдельные базы и запустить сервер со всеми тремя —

```bat
confdb extract main.cf --db main.db
confdb extract ext.cfe --db ext.db
confdb extract proc.epf --db proc.db
1confdb-knw main.db ext.db proc.db
```

— после чего LLM видит метаданные и код всех трёх и может, например,
искать методы расширения (`find_methods` с `db='ext'`) поверх основной
конфигурации. Специальное значение `db='*'` выполняет инструмент сразу
по всем открытым базам (ответ приходит секциями по базам) — один вызов,
чтобы сравнить основную конфигурацию с расширениями. Если база
пересобрана (повторный `extract`), её достаточно закрыть и открыть
заново: `db_close` + `db_open`.

**Идентификатор базы в ответах:** каждый ответ инструмента данных начинается
с заголовка `=== база <алиас> (<путь>) ===`, идентифицирующего источник данных.
Если база входит в группу, заголовок называет и её —
`=== группа <имя> / база <алиас> (<путь>) ===`, а при вхождении в несколько
групп — `=== группы A, B / база …`.
Это позволяет LLM сравнивать конфигурации (типовая vs доработанная, основная vs
расширение) и понимать, в какой базе находится метод или объект. Например:

```
=== база основная (C:\path\main.db) ===
Справочник.Контрагенты: 150 объектов

=== база расширение (C:\path\ext.db) ===
Справочник.Контрагенты: 155 объектов
```

Инструменты управления базами (`db_list`, `db_open`, `db_use`, `db_close`) не
содержат заголовок — они сами управляют базами.

#### Группы конфигураций: несколько наборов баз одновременно

Группа объединяет связанные базы (основная конфигурация + расширения +
обработки) под одним именем. Групп может быть открыто **несколько
одновременно** — например две разные конфигурации или две версии одной, —
и деление при этом сохраняется: сервер знает, какая база в какой группе,
и печатает это в `db_list`, в `group_list` и в заголовке каждого ответа.

- запуск с группами: `1confdb-knw --group УНФ=unf.db --group УНФ=unf_ext.db
  --group БП=bp.db` — повтор флага добавляет базу в ту же группу, несколько
  путей можно перечислить через `;`. Первая группа становится активной, а её
  первая база — активной базой;
- запрос к ОДНОЙ группе: параметр `group='БП'` у инструмента данных — он
  выполнится по всем базам группы и вернёт ответ секциями
  `=== группа БП / база <алиас> (<путь>) ===`;
- запрос сразу ко всем группам: `group='*'` — секции по группам, каждая со
  своими базами (в отличие от `db='*'`, который смешивает все открытые базы);
- **без `group` выполняется только активная база**, а не вся активная группа:
  при нескольких открытых группах группу нужно называть явно. `group_use`
  переключает активную группу и делает её первую базу активной;
- отказ одной базы не рвёт групповой вызов (`group=<имя>`, `group='*'`,
  `db='*'`): её секция несёт `ошибка [КАТЕГОРИЯ]: …` (`DB_LOCKED` —
  транзитная, тот же вызов может пройти повторно), остальные базы отвечают
  штатно, а ответ заканчивается строкой `баз с ошибкой N из M: <алиасы>`,
  чтобы частичный ответ не читался как полный. `isError` вызов получает
  только когда отказали **все** базы — их секции при этом остаются видны;
- на ходу: `group_create`, `group_add_db`, `group_remove_db`, `group_list`,
  `group_use`, `group_close` (удаление группы базы не закрывает).

`compare_object` и `extension_diff` групп не знают: они принимают явные
алиасы баз (`db_left`/`db_right`, `extension_db`/`base_db`), которые
берутся из `db_list` или `group_list`.

В консольном интерфейсе наборы баз сохраняются в **именованные группы**
(пункт 4 главного меню): одна база может входить в несколько групп. Пункт 1
запускает сервер с **несколькими группами сразу** — номер отмечает или
снимает группу, `*N` делает N-ю выбранной первой (её база станет активной),
`m` добавляет отдельные базы вне групп. В сетевом режиме панель после
запуска позволяет подключать/закрывать базы и работать с группами из
конфига без перезапуска сервера: добавить группу (остальные группы и базы
останутся открытыми), заменить весь набор одной группой, убрать группу (её
базы закроются, если не нужны другим группам) и сделать группу активной.

Пример конфигурации MCP-клиента, в т.ч. через SSH:

```json
{
  "mcpServers": {
    "1confdb-knw": {
      "command": "ssh",
      "args": ["user@host", "python", "-m", "confdb.mcp_server", "/path/out.db"]
    }
  }
}
```

### Сетевой режим (когда stdio не подходит)

Сервер слушает порт и отдаёт MCP по HTTP (Streamable HTTP: `POST /mcp`;
legacy SSE для старых клиентов: `GET /sse` + `POST /messages`):

```bat
1confdb-knw out.db --port 8765
```

С другой машины подключение — через SSH-туннель:

```bat
ssh -L 8765:127.0.0.1:8765 user@host
```

```json
{
  "mcpServers": {
    "1confdb-knw": { "url": "http://127.0.0.1:8765/mcp" }
  }
}
```

По умолчанию слушает `127.0.0.1` (без аутентификации, база read-only);
`--host 0.0.0.0` открывает порт наружу — используйте только в доверенной сети.
В консольном интерфейсе — пункт 1 → «Сеть (HTTP-порт)».

Запросы выполняются по одному за раз: соединения баз и приставных шардов FTS на
сервер общие, поэтому вызовы инструмента сериализованы — в stdio, в HTTP и когда
консольный интерфейс обращается к работающему серверу. Долгий запрос (`sql` по
большой таблице, поиск по телам в базе без индекса) задерживает остальных
клиентов; параллельные подключения работу не ускоряют.

Опции `extract`:

- `--db FILE` — записать результат в SQLite;
- `--dump DIR` — сохранить распакованное дерево файлов (нужен хотя бы один из `--db`/`--dump`);
- `--temp-dir DIR`, `--keep-temp` — рабочий каталог стадий 0–1 и его сохранение.
  Без `--temp-dir` он создаётся рядом с базой (`--db`) или дампом (`--dump`), а не
  в `%TEMP%`: на системном томе удаление ~125 тысяч файлов рабочего каталога стоит
  ~30 с и почти не распараллеливается, на несистемном — ~10 с, и прогон УНФ целиком
  занимает 70 с вместо 97 с. Если каталог результата недоступен — откат на `%TEMP%`;
- `--prefix STR` — снять префикс с имён объектов;
- `--store-blobs` — хранить бинарные файлы (картинки, макеты) в БД как BLOB;
- `--workers N` — число процессов стадии 3 и записи БД (по умолчанию — результат
  `confdb bench` или 1; на многоядерной машине несколько процессов ускоряют разбор
  в несколько раз). В консольном интерфейсе — меню «Опции извлечения». При вызове
  `extract()` из собственного скрипта на Windows с `workers > 1` вызов должен быть
  обёрнут в `if __name__ == '__main__':` (требование multiprocessing spawn).
- `--no-fts` — не строить FTS-индекс по телам методов. Индекс — приставные файлы
  `<база>.fts\0.db…`, по одному на процесс (на УНФ 7.5 с в 8 шардов, ~1.1 ГБ); сама
  база остаётся одним файлом и без индекса работоспособна — поиск по телам идёт
  полным проходом (~0.3 с на запрос). Достраивается позже командой
  `confdb fts <база> [--workers N]`, каталог `.fts` можно удалить в любой момент.
- `--dump-indent` — писать JSON дампа с отступами, как это делает v8unpack. Нужно
  только для побайтового сравнения дампов при проверке эквивалентности декодера:
  по умолчанию вывод компактный, с ним стадия 3 быстрее (28.0 с против 30.8 с на УНФ),
  а дерево дампа примерно втрое меньше. На содержимое базы флаг не влияет.
- `--force` — пересобрать базу, даже если она уже собрана из этого же файла.
  Без флага `extract` сравнивает SHA-256 исходника с `source.file_sha256` целевой
  базы и при совпадении не запускает распаковку вовсе (~70 с на УНФ против 1,7 с
  на отпечаток).

## Синтакс-помощник платформы (.hbk → syntax.db)

Отдельный конвейер (`src/confdb/hbk/`) — база знаний УРОВНЯ ПЛАТФОРМЫ: что
вообще даёт встроенный язык и стандартная библиотека 1С, независимо от
содержимого конфигурации. Источник — файл контекстной справки платформы
`shcntx_ru.hbk` (из поставки 1cv8, проверено на 8.3.26.1498), результат —
`syntax.db`: ~25 300 тем (типы, члены глобального контекста, поля системных
таблиц), ~9 100 параметров, ~110 000 перекрёстных ссылок, FTS5-поиск. Эти же
данные отдаёт MCP-сервер (инструменты `syntax_*`, ключ `--syntax-db`) и CLI:

```bat
:: 1. Распаковка .hbk (чистый Python: стандартный zipfile и 7-Zip файл не читают)
confdb hbk unpack hbk\shcntx_ru.hbk -o extracted
confdb hbk unpack hbk\shcntx_ru.hbk --list          :: только список файлов
confdb hbk unpack hbk\shcntx_ru.hbk --verify-only   :: только проверка CRC

:: 2. Сборка базы (~1,5 мин) и контроль качества
confdb hbk build extracted --db syntax.db
confdb hbk check syntax.db                          :: exit code 0 = всё в порядке
confdb hbk check syntax.db --quick                  :: только структурные проверки

:: 3. Запросы к готовой базе (путь по умолчанию: syntax.db, затем hbk\syntax.db)
confdb hbk search "транзакци"                       :: нечёткий поиск
confdb hbk show 24331                               :: карточка темы
confdb hbk tree 1 -d 2                              :: поддерево темы
confdb hbk repl                                     :: интерактивный обход (REPL)
```

### Почему свой распаковщик .hbk

Файл `.hbk` — не обычный ZIP: перед архивом идёт заголовок 1С (1656 байт),
поэтому все offset'ы central directory относительные, а после основного ZIP
лежат хвостовые сегменты (индексные «паки» 1С) с собственными EOCD —
стандартный `zipfile` берёт последний EOCD и падает с «Bad magic number for
central directory». Алгоритм `hbk/unpack.py`: найти все EOCD (`PK\x05\x06`) →
для каждого с конца файла проверить целостность (CD из n записей заканчивается
ровно на EOCD; по каждому base+local_ofs стоит `PK\x03\x04`) → первый валидный
сегмент = основной архив → извлечение с проверкой CRC32 и размеров. Имена
записей: bit 11 = UTF-8, иначе cp866 (OEM-кодировка 1С), fallback cp437;
пути проверяются на выход за пределы каталога назначения.

### Формат выгрузки справки (extracted/)

Каждой теме соответствует пара `<тема>.html` + `<тема>.st`:

- **HTML-страницы** — разметка на CSS-классах `V8SH_*`: `V8SH_pagetitle`
  (заголовок страницы), `V8SH_title`/`V8SH_heading` (имя вида
  «НачатьТранзакцию (BeginTransaction)»), `V8SH_chapter` (секции: «Синтаксис»,
  «Параметры», «Возвращаемое значение», «Описание», «Пример», «Доступность»,
  …), `V8SH_rubric` (блок параметра). Хвост после `<HR>` («Методическая
  информация») отрезается. Кодировка — UTF-8 с BOM (`utf-8-sig`);
- **`.st`** — краткая сигнатура метода литералом 1С: извлекаются строки при
  `node[0] in ("ru","en")`;
- **`__categories__`** (в каждом каталоге) — литерал 1С: порядок
  перечисления файлов + доступность по режимам (`CONF_ENTERPRISE`,
  `CONF_WEB_ENTERPRISE`, `CONF_MOBILE_ENTERPRISE`, …) + версия появления
  («8.0.4»); режимы и версия хранятся в `topics.modes` (JSON);
- **групповые папки** `methods/ properties/ events/ ctors/ formparams/
  fields/ params/` — группы членов типа; вид листа определяется ближайшей
  сверху групповой папкой;
- **владелец каталога** — файл `../<имя>.html`, если существует (`Global
  context.html` владеет `Global context/methods/...`); по владельцам строится
  дерево `parent_id`;
- **ссылки** — `href="v8help://SyntaxHelperContext/<путь>"` (внутренние) и
  `v8help://SyntaxHelperLanguage/...` (книга языка, не извлекается); виды:
  `see` («См. также»), `type` (после «Тип:»), `body` (остальные). В текстах
  карточек на месте разрешённых ссылок стоят отметки «(id=N)» — готовый
  адрес для перехода (`syntax_card(id=N)` / `confdb hbk show N`).

### Схема syntax.db

| Таблица | Содержимое |
|---|---|
| `topics` | Все темы: `path` (уникален), `parent_id` (дерево), `kind`, `name_ru`/`name_en`, `title`, `num`, `syntax`, `signature_ru`/`signature_en` (из .st), `returns`, `description`, `example`, доступность по платформам — булевы колонки `av_server`, `av_thick_client`, `av_thin_client`, `av_web_client`, `av_external_connection`, `av_mobile_client`, `av_mobile_app_client`, `av_mobile_app_server`, `av_mobile_autonomous_server`, `av_integration` — плюс `availability_note`, `since`, `modes` (JSON), `sort` |
| `params` | Параметры методов/конструкторов: `name`, `optional`, `type_text`, `type_id` (ссылка на тему типа), `description`; нераспознанная секция параметров — одна строка с `name IS NULL` (fallback) |
| `links` | Перекрёстные ссылки: `src_id`, `dest_id` (NULL для битых/внешних), `href`, `kind` (`see`/`type`/`body`) |
| `fts` | FTS5 по `name_ru`, `name_en`, `signature_ru`, `signature_en`, `syntax`, `description`; `rowid` = `topics.id` |
| `meta` | `source`, `built_at`, `platform`, `topics`, `kinds` (JSON), `links`, `links_broken`, `links_lang`, `params`, `av_unknown` (ожидается 0), `fts`, `extractor_version` |

Виды тем (`topics.kind`): `root` (ровно 2: «Объекты» и «Таблицы»), `section`,
`group`, `type` и члены типов: `method`, `property`, `event`, `ctor`,
`formparam`, `field`, `param`. База НЕ является базой знаний confdb (нет
`meta_object`, своя ревизия не штампуется) — сервер открывает её отдельно и
в группы конфигураций она не входит.

### Контроль качества (`confdb hbk check`)

Пороги, ниже которых сборка считается браком: ровно 2 корня; нет
сирот/самоссылок/битых `parent_id`; сигнатуры .st почти у всех членов типов
(допуск −40); синтаксис у ≥95 % методов; флаги доступности у всех методов;
описание у ≥90 % тем (кроме корней); fallback-параметров ≤50; битых внутренних
ссылок ≤100; type-ссылок >1000; точечные проверки на эталонных темах
(`BeginTransaction9.html`, `Ref23.html`) и работоспособность FTS. Числовые
пороги и эталоны настроены на полную базу shcntx_ru.hbk — для малых баз
`--quick` оставляет структурные проверки.

### Нечёткий поиск и карточки

Поиск сливает три метода с приоритетами: FTS5-префиксы (`"слово"*`, OR между
словами, ранжирование bm25) → подстрока в `name_ru`/`name_en`/`syntax` →
расстояние Левенштейна по именам (для опечаток; слова короче 3 букв не
учитываются, дистанция 1–2). В строке результата после имени выводится
родитель темы («Колонки (Columns) — ТабличноеПоле») — одинаковые члены разных
типов различимы; пометка «+» у вида — у темы есть потомки. Карточка темы
включает breadcrumb от корня, вид, версию, доступность (список платформ из
флагов `av_*`), примечание, синтаксис, сигнатуры RU/EN, возвращаемое
значение, параметры (с именем типа по ссылке), описание, пример и все ссылки
с id целей для перехода. REPL (`confdb hbk repl`): «поиск/открыть/дети/вверх/
показать/путь/дерево», ввод номера без команды открывает элемент последнего
списка.

### MCP-инструменты и подключение

`--syntax-db <путь>` при старте сервера (или ключ `syntax_db` в
`~/.confdb/config.json` — TUI подставляет его сам) подключает базу и добавляет
три инструмента: `syntax_search(query, limit)` — тот же нечёткий поиск,
`syntax_card(id)` — полная карточка темы, `syntax_children(id)` — дети темы
(без id — два корня). Без подключённой базы инструменты отвечают внятным
сообщением с инструкцией (это факт настройки сервера, а не ошибка запроса).
Разделение труда для модели: базы конфигурации говорят, что содержит ЭТА
конфигурация, а синтакс-помощник — что предлагает САМА платформа (существует
ли глобальный метод, его точная сигнатура, параметры, контексты выполнения и
с какой версии доступен). Файлы `.hbk` и готовая `syntax.db` лежат в каталоге
`hbk/` (не публикуется в git — собирается из файла своей платформы).

## Бенчмарк и автонастройка

`confdb bench <file>` один раз прогоняет стадии 0/1, затем нелинейный сэмпл
объектов верхнего уровня (шаг по всему списку + покрытие всех типов объектов,
чтобы задеть и лёгкие справочники, и тяжёлые формы/отчёты) через стадию 3 и
запись БД при 1/2/4/8/CPU процессах. Лучшее число процессов сохраняется в
`~/.confdb/config.json` и подставляется по умолчанию в `extract` и в консольный
интерфейс; `--workers N` переопределяет вручную.

Стадии конвейера (повторяют v8unpack, только распаковка):

0. чтение внешних V8-контейнеров (32/64-бит) в файлы как есть;
1. inflate (raw deflate) + рекурсивные вложенные контейнеры;
3. декодирование метаданных: скобкофайлы `{}` → JSON, тексты модулей → `.bsl`.

## Веб-интерфейс (`confdb web`)

Повторяет функции консольного интерфейса (TUI) в браузере и опирается на тот же
общий слой логики `ui_core.py` — поэтому доработка логики достаётся обоим
интерфейсам сразу (правило пользователя от 2026-11-12). Только стандартная
библиотека: `http.server` раздаёт JSON-API и одностраничное приложение
`webui.html` (vanilla JS, без внешних зависимостей и CDN — работает офлайн).

Запуск: `confdb-web.bat` (или `confdb web`, или `python -m confdb.webui`).
По умолчанию слушает `127.0.0.1:8766` и открывает браузер; `--port N` — другой
порт, `--no-browser` — не открывать, `--host` — адрес (оставляйте локальным).

Вкладки (соответствуют меню TUI):

- **MCP-сервер** — запуск с выбором нескольких групп и/или отдельных баз и порта;
  панель работающего сервера: URL и конфигурация клиента, список баз (сделать
  активной/закрыть, отметка «устарела»), открыть ещё базу, группы конфигураций
  (создать/добавить базу/убрать/активировать), применение групп из конфига
  (добавить/заменить всё), остановка. Остановка закрывает соединения (`close_all`)
  и убирает pidfile — файлы баз свободны для пересборки;
- **Извлечение** — файл 1С или каталог выгрузки (автоопределение), путь базы и
  дампа, запуск; отдельно — достроить FTS-индекс готовой базы;
- **Каталог cf** — каталог с файлами 1С, сканирование по SHA-256 (статусы
  «актуальна»/«устарела»/«новая»), выборочное или массовое извлечение новых и
  устаревших с заменой sqlite;
- **Группы баз** — создать/изменить/удалить именованные наборы баз;
- **Настройки** — число процессов, рабочий каталог, префикс, каталог cf,
  keep_temp/store_blobs/skip_errors/build_fts, каталоги баз, бенчмарк.

Тяжёлые операции (извлечение, пакетное извлечение, сканирование, FTS, бенчмарк)
выполняются фоновой задачей (`TaskManager`, одна за раз): интерфейс опрашивает
`GET /api/task` и показывает живой журнал (перехват stdout). Настройки и группы
хранятся в том же `~/.confdb/config.json`, что использует TUI.

## Схема базы данных

Ревизия схемы штампуется в сам файл базы: `PRAGMA user_version = writer.SCHEMA_VERSION`
(с 2026-10-08). MCP-сервер отвечает только на базы своей ревизии, а на устаревшую
возвращает просьбу пересобрать её (`confdb extract <файл> --db <база> --force`) — вместо
ошибки схемы посреди запроса. Совместимого режима чтения старых схем нет: новые колонки
(например `role_right.target_flags`) заполняются только из исходника, миграции не
существует. У баз, собранных до появления штампа, `user_version = 0` — они считаются
устаревшими. Ревизию открытых баз показывают `db_list`, `db_open` и список баз в TUI.

С ревизии 7 (2026-10-09) в таблицу `source` добавлена колонка `extractor_version` —
версия извлекателя (`confdb.__version__`). `configuration_info` показывает ревизию
схемы, версию извлекателя и доступные возможности базы (права ролей, FTS по телам
методов, XDTO, СКД). У баз до ревизии 7 `extractor_version` будет NULL.

Ревизия 8 (2026-10-10) — `meta_subobject` (подобъекты, на которые могут указывать
права: операции веб-сервисов, методы и шаблоны URL HTTP-сервисов, каналы сервисов
интеграции) и `role_right.target_subobject_id`. Ревизия 9 (2026-11-07) — поддержка
выгрузки конфигурации в файлы: таблицы `dump_state`/`dump_file` (состояние файлов
выгрузки для инкрементального обновления), колонка `attribute_ref.target_path`
(цель ссылки по пути — позволяет переразрешить ссылку, когда объект добавлен
позже ссылки), индекс `ix_meta_object_uuid`; внешние ключи `attribute_ref.object_id`
и `role_right.target_*` переведены с `ON DELETE CASCADE` на `ON DELETE SET NULL` —
строки ссылок и прав ДРУГИХ объектов переживают переустановку цели при
инкрементальном обновлении и переразрешаются по `target_path`/`target_uuid`.

- `source` — исходный файл: путь, дата, тип/имя/uuid корневого объекта, версия извлекателя;
- `meta_object` — объект метаданных: `path` (например `Catalog/Контрагенты/CatalogForm/ФормаЭлемента`),
  `type` (Catalog, Document, CommonModule, …), `type_ru` (русское имя «как в конфигураторе»:
  Справочник, Документ, Общий модуль, …), `name`, `uuid`, `comment`, `obj_version`,
  `header_json` (полный разобранный заголовок; в базах из выгрузки в файлы —
  исходный XML объекта), `parent_id` + `ord` (иерархия и порядок
  братьев — как в дереве конфигуратора). `uuid` КОРНЯ — uuid метаданных
  Configuration (в cf — `file_uuid` заголовка, а не внутренний uuid файла
  контейнера): один и тот же в cf-базе и в базе из выгрузки, поэтому права на
  конфигурацию разрешаются в корневой объект в обеих;
- `meta_attribute` — реквизиты объекта: `ord`, `name`, `type_str` в порядке объявления.
  Примитивы — Строка(50)/Число/Дата/Булево; ссылки — `Ссылка: <путь>` (таблица ссылочных
  uuid из потока `.10` корневого объекта, коллизии имён дизамбигуируются по типу объекта);
  определяемые типы — `ОпределяемыйТип: <путь> (<состав>)` (состав раскрывается);
  составные типы — члены через ` | `; обобщённые типы платформы («ЛюбаяСсылка» и т.п.),
  чей uuid не соответствует ни одному объекту конфигурации, — `Ссылка` (это не ошибка
  извлечения, у такого типа нет конкретной цели); `Ссылка: <имя> (объект не найден
  в базе)` — имя цели известно из таблицы `.10`, но самого объекта в этой базе нет
  (типично для ссылки из расширения на объект основной конфигурации); `NULL` —
  в заголовке объекта описание типа этого реквизита отсутствует; `uuid` — собственный
  идентификатор поля в метаданных: по нему цель права роли (`role_right.target_uuid`)
  разрешается в конкретный реквизит, `NULL`, когда в заголовке поля uuid нет;
- `attribute_ref` — связи реквизитов с объектами метаданных: `uuid` (ссылочный uuid
  из дескриптора типа, для составных/определяемых типов — по строке на член) и
  `object_id` — объект, на который ведёт ссылка (NULL для абстрактных типов);
  `target_path` — путь цели (заполняется в базах из выгрузки: ссылка разрешается
  даже когда объект добавлен позже неё — инкрементальное обновление);
  зависимость «реквизит ↔ объекты» строится join'ом без разбора строк `type_str`;
- `enum_value` — значения перечислений (`ord`, `name`) в порядке объявления;
- `predefined` — предопределённые элементы из «Предустановленные данные.bin»: `ord`
  (номер в обходе в глубину), `parent_ord` (ord родителя; NULL только у корневого узла
  «Счета»/«Элементы», который элементом не является), `uuid` элемента, `name`, `code`,
  `display`;
- `predefined_subconto` — виды субконто предопределённого счёта плана счетов:
  `predefined_id`, `ord`, `uuid` вида субконто, `kind_id` — предопределённый элемент
  плана видов характеристик, которым он разрешается, `flags` — включённые флаги через
  «;» («Суммовой», «Валютный», «Количественный»);
- `common_target` — привязка общих реквизитов к объектам метаданных;
- `meta_tabular` — табличные части объекта (`ord`, `name`, `uuid`) в порядке объявления;
  поля табличных частей лежат в `meta_attribute` с заполненной колонкой
  `tabular` (имя секции) — цепочки вида `Т.Товары.Наименование` в запросах
  проверяются по этим данным; `uuid` секции разрешает право роли, заданное на
  табличной части.
- `module` — паспорт модуля: `code_name` (obj, mgr, mod, con, app …) и для общих
  модулей `context` (Сервер/Клиент/Вызов сервера/…), плюс `body` — текст модуля как есть
  без кода методов: комментарии, препроцессор `#Если…`, `#Область…`, директивы и сигнатуры
  вида `Процедура Имя(п1, п2) Экспорт` сохранены; подстановка `method.body` вместо каждой
  сигнатуры восстанавливает исходный модуль;
- `method` — только процедуры/функции: вид, имя, сигнатура, `is_export`, `directives`
  (строка `&НаКлиенте, &НаСервере` без скобок), `description` (блок комментариев
  непосредственно над методом, как есть с `//`), `line_start/line_end`, `body` — строго
  с `Процедура/Функция` по `КонецПроцедуры/КонецФункции`; `#…` и комментарии вне тела
  в метод не попадают;
- `subsystem_content` — состав подсистем (ссылки на объекты в порядке объявления) —
  для обхода дерева подсистем, как в конфигураторе;
- `skd_query` — запросы, извлечённые из макетов СКД объекта (`ord`, `query`), —
  для проверки корректности запросов 1С;
- `role_right` — объектные права ролей: из файла `Role/<имя>/Role.0.c1brace`
  (cf-базы) или из `Roles\<имя>\Ext\Rights.xml` (базы из выгрузки;
  `role_rights_state.version='xml'`). Хранятся
  только ЯВНЫЕ записи (sparse): отсутствие строки означает «право не задано», а не
  «запрещено». **Три пространства uuid — не объединять в один словарь:**
  (1) `right_uuid` — идентификатор ВИДА права платформы (один на всю платформу;
  словарь имён `rights.RIGHT_NAMES` пересобран 2026-11-07 по подтверждённым
  источникам: uuid→eng — CSP-майнинг по паре «выгрузка+cf», eng→rus — справка
  «ПравоДоступа»; в выдаче печатается `право Чтение=1`);
  (2) `target_uuid` — uuid ЦЕЛИ права в этой
  конфигурации (объект/реквизит/поле ТЧ/ТЧ, на которое право распространяется; печатается
  как русский путь или `цель uuid ...` при неразрешённой цели); (3) `role_id` — uuid РОЛИ
  как объекта метаданных (строка в `meta_object` где `type='Role'`). Цель права — объект,
  его реквизит/поле табличной части или его табличная часть: `target_object_id` —
  объект-владелец (заполнен и для подобъекта, поэтому все права, затрагивающие объект,
  выбираются одним условием), `target_attr_id`/`target_tabular_id` — сам подобъект,
  `target_uuid` — uuid цели как он записан в роли (подобъект, которого проект не извлекает,
  остаётся только с ним); `value` — значение права, `sub_index`/`collection_uuid` —
  адресация «подобъект №-K внутри коллекции», `target_flags` — флаги записи цели дословно,
  без толкования (их смысл не подтверждён; без них две цели с одним uuid слились бы в одну),
  `rls_text` — ограничение доступа на уровне записей для этой цели и права;
- `role_rls_template` — именованные шаблоны RLS роли (`name`, `text`);
- `role_rights_state` — состояние извлечения прав каждой роли: `parsed=0` — данные
  недоступны (файла прав нет или формат не распознан, причина в `error`),
  `parsed=1` при `rights=0` — права роли действительно не заданы;
- `xdto_type`, `xdto_property`, `xdto_import` — содержимое пакетов XDTO
  (файл `XDTOPackage.bin` — это открытый XML, реверс бинарного формата не
  потребовался): типы `objectType`/`valueType`/`typeDef` с базовым типом,
  ограничениями и значениями перечислений, их свойства (обязательность,
  признак списка, форма — атрибут или элемент, вложенные анонимные типы) и
  импортируемые пространства имён; `type_id IS NULL` означает свойство,
  объявленное самим пакетом вне типов; целевое пространство имён пакета
  берётся из его `header_json`. Инструменты `xdto_of` и `find_xdto`;
- `file` — прочие файлы дампа/выгрузки (help.html, инфо-JSON, Form.xml, Rights.xml,
  картинки): путь (в cf-базах — относительно дерева стадии 3, в базах из выгрузки —
  относительно корня выгрузки), тип, размер, содержимое для текстовых (BLOB — только
  при `--store-blobs`); в базах из выгрузки содержимое макетов `Template.*` и
  `ConfigDumpInfo.xml` не хранится (запросы СКД извлечены в `skd_query`, а сами
  листы — мегабайты справочных данных, которые никто не читает);
- `dump_state` (одна строка) — каталог выгрузки и время последнего обновления;
  наличие строки отличает базу из выгрузки от cf-базы: `confdb update` без неё
  делает полную пересборку;
- `dump_file` — состояние каждого файла выгрузки: `path` (относительный,
  разделитель `/`), `granule` (объект верхнего уровня — гранула инкрементального
  обновления; `''` — корень), `size`, `mtime_ns`, `sha256`. Обход обновления
  сверяет размер/mtime и хэширует только подозрительные файлы;
  `source.file_sha256` базы из выгрузки — манифест состава (SHA-256 по
  отсортированным парам «путь + хэш» всех файлов), одинаково считается при
  сборке и при обновлении.

Пример запроса:

```sql
-- реквизиты справочника с типами
SELECT a.name, a.type_str
FROM meta_attribute a JOIN meta_object o ON o.id = a.object_id
WHERE o.path = 'Catalog/Контрагенты' ORDER BY a.ord;

-- краткое представление модуля (текст без кода методов)
SELECT m.body FROM module m JOIN meta_object o ON o.id = m.object_id
WHERE o.path = 'Catalog/Контрагенты' AND m.code_name = 'obj';

-- тело конкретного метода
SELECT mt.body FROM method mt JOIN module m ON m.id = mt.module_id
JOIN meta_object o ON o.id = m.object_id
WHERE o.path = 'Document/Заказ' AND m.code_name = 'obj'
  AND mt.name = 'ПриПроведении';
```

## Состав

- `src/confdb/v8` — ядро распаковки (контейнеры 1С, inflate, скобкофайлы, метаданные);
  uuid корня для базы — `file_uuid` заголовка (uuid метаданных Configuration — тот же,
  что у корня базы из выгрузки), модуль перечисления и критерия отбора — модуль
  менеджера (`Enum.mgr.bsl`, code_name `mgr` — как в dump-базе);
- `src/confdb/extract.py` — конвейер стадий 0/1/3 (контейнеры → inflate → разбор). Рабочий
  каталог по умолчанию создаётся на томе результата (`make_temp_dir`), а не в `%TEMP%`, и
  удаляется параллельно (`remove_tree`): удаление ~125 тыс. файлов стоит ~30 с на системном
  томе против ~10 с на другом. Здесь же отпечаток источника — `file_sha256` (1.7 с для
  885 МБ) пишется в `source.file_sha256`, а `check_same_source(src, db, force)` позволяет
  CLI и TUI не распаковывать тот же файл повторно; в старых базах отпечатка нет, и это
  читается как «неизвестно», а не как «файл другой»;
- `src/confdb/__main__.py` — CLI: `extract`, `update`, `check`, `fts`, `bench`, `hbk`, `1confdb-knw`;
- `src/confdb/hbk/` — синтакс-помощник платформы (файлы справки `.hbk` → `syntax.db`):
  `unpack.py` (ZIP со смещением на заголовок 1С: скан EOCD, валидация сегментов, CRC32,
  cp866-имена), `build.py` (HTML в разметке `V8SH_*`, сигнатуры `.st`, `__categories__` →
  темы/параметры/ссылки/FTS5), `check.py` (пороги качества сборки), `query.py` (нечёткий
  поиск, карточка темы, дерево, REPL — функции возвращают текст для CLI и MCP);
  данные — каталог `hbk/` в корне (не в git); раздел «Синтакс-помощник платформы»;
- `src/confdb/dump/` — сборка базы из ВЫГРУЗКИ конфигурации в файлы (формат конфигуратора
  «Выгрузка конфигурации в файлы», иерархический): `model.py` (реестры классов и сканер
  дерева: 45 каталогов классов → типы БД, формы `<Класс>Form` у обработок особый тип `Form`,
  команды — метаданные встроены в XML родителя, вложенные подсистемы рекурсивно; гранула
  обновления = объект верхнего уровня со всем деревом), `xmlmeta.py` (XML-парсер: типы
  реквизитов в тех же строках, что и cf-сборка — «Строка(10)», «Ссылка: Catalog/Х»,
  «ОпределяемыйТип: … (…)» с раскрытием состава; поля/ТЧ/перечисления/предопределённые
  с субконто; контексты общих модулей), `build.py` (полная сборка: фазы объекты → модули
  в пуле процессов → файлы+хэши dump_file → межобъектные связи → права; `header_json`
  хранит исходный XML, ссылки разрешаются UPDATE по `attribute_ref.target_path`; строки
  всех общих таблиц пишутся через `writer.INSERT_SQL` — те же INSERT, что и cf-путь;
  база создаётся в WAL), `rights.py` + `rights_map.py` (права из текстового `Ext\Rights.xml`:
  цели разрешает общий `rights.TargetResolver.resolve` по точечным именам, uuid видов
  прав — накопанная биекция eng→uuid, подтверждённая
  RLS-якорями; true→'1', false→'-1' — та же sparse-семантика, что у c1brace),
  `update.py` (инкрементальное обновление: быстрый stat-обход, SHA-256 только изменённых
  файлов, переустановка грязных гранул DELETE-каскадом + вставка, перелинковка
  `attribute_ref`/`role_right`/субконто по uuid, пересчёт составов подсистем и общих
  реквизитов, права затронутых ролей перечитываются; FTS пересобирается поколениями
  шардов — живой сервер переключается сам); СКД-запросы берутся из текстового
  `Ext\Template.xml` тем же regex, что и из .cf, XDTO — из того же `Package.bin`;
- `src/confdb/db/writer.py` — схема SQLite и запись результата: пакетные вставки, разбор BSL
  в несколько процессов (`workers`); права ролей пишутся после объектов и разрешаются
  общим резолвером `rights.TargetResolver.resolve_uuid` (цель в скобкофайле — uuid);
  ревизия схемы (`SCHEMA_VERSION`) штампуется в файл базы (`PRAGMA user_version`).
  Общий слой записи строк для обоих конвейеров (cf-базы и базы из выгрузки):
  `INSERT_SQL` — список колонок и INSERT каждой общей таблицы в одном экземпляре,
  `insert_rows` — пакетная вставка; `dump/build.py` и `dump/rights.py` пишут
  строки тем же SQL.
  Приставной FTS-индекс по телам методов (`build_fts_index`) пишется ШАРДАМИ
  `<база>.fts\<k>.db` с манифестом `index.json` (последним — незавершённая сборка
  видна как «индекса нет»); пересборка у живого сервера создаёт новое ПОКОЛЕНИЕ
  шардов `g<N>_<k>.db` и переключает манифест — открытые соединения не блокируют
  подмену (Windows), старые файлы удаляются best-effort;
- `src/confdb/query_lang.py` — разбор и семантический контроль языка запросов 1С
  (подкоманда `confdb check`);
- `src/confdb/mcp_server.py` — MCP-сервер `1confdb-knw <база…>`: read-only инструменты,
  самомописываемый (схема, глоссарий и порядок работы отдаются в `initialize.instructions`).
  Несколько баз (алиас на базу, необязательный параметр `db`, `db='*'` — по всем сразу) и
  ГРУППЫ конфигураций: `--group ИМЯ=ПУТЬ` (повторяемый) открывает несколько групп,
  `group=<имя>` опрашивает одну, `group='*'` — все, а без `group` работает только активная
  база (`group_use` переключает активную). Шесть поисковых инструментов страничные
  (`limit` 1..200 и `offset`, последняя строка ответа называет общее число совпадений и
  следующий `offset`); кросс-базовые инструменты принимают явные алиасы (`compare_object`,
  `extension_diff`); ошибки категоризованы (`error_text`), `SQLITE_BUSY` повторяется
  (`call_with_retry`). Транспорт — stdio, `--port N` включает HTTP/SSE; вызовы
  инструментов сериализованы общей блокировкой (`_synchronized`): соединения баз и
  приставных шардов FTS на сервер общие, а потоков несколько — HTTP-обработчик
  создаётся на запрос, панель работающего сервера в TUI дёргает тот же объект.
  **Hot reload**: на каждый вызов инструмента сервер сверяет `PRAGMA
  data_version` и при чужом COMMIT сбрасывает производные кэши (счётчики,
  контексты запросов/BSL, индексы подписок и uuid, FTS-манифест) — база из
  выгрузки обновляется `confdb update` без остановки сервера; при старте
  пишется pidfile `<база>.server.json` (pid/порт/алиас), который читает
  `update`. Отдельно от баз конфигурации подключается синтакс-помощник
  платформы (`--syntax-db syntax.db`, либо ключ `syntax_db` в
  `~/.confdb/config.json` — TUI подставляет его при запуске сервера):
  инструменты `syntax_search`/`syntax_card`/`syntax_children` работают с
  одной статичной базой `hbk/query` и в группы/fan-out не входят;
- `src/confdb/ui_core.py` — **общий слой логики обоих интерфейсов** (TUI и веб): состояние
  `~/.confdb/config.json`, кандидаты файлов/баз, сканирование каталога cf по SHA-256
  (`scan_cf_sources`), оркестрация извлечения (.cf и выгрузка), FTS, бенчмарк, группы баз,
  `ServerRunner` — жизненный цикл MCP-сервера (HTTP) с `close_all` при остановке. Правило
  (пользователь, 2026-11-12): TUI и веб-интерфейс развиваются вместе — новая логика интерфейса
  добавляется сначала сюда, затем подключается в обоих фронтах;
- `src/confdb/tui.py` — консольный интерфейс, тонкая обёртка над `ui_core` (выбор пользователя:
  консоль, а не desktop-GUI; tkinter не предлагать). В списках файлов и баз число выбирает
  элемент, а любой другой текст читается как введённый путь. Запуск MCP выбирает несколько
  групп баз сразу (в сервер они попадают как `--group` в stdio-режиме и как `McpServer(groups=…)`
  в сетевом), а панель работающего сервера добавляет, заменяет все, удаляет и активирует группу
  без перезапуска;
- `src/confdb/webui.py` + `webui.html` — веб-интерфейс (stdlib `http.server` + одностраничное
  приложение на vanilla JS, русский язык, только localhost): те же функции, что в TUI, поверх
  `ui_core`. Запуск `confdb web` / `confdb-web.bat` (порт по умолчанию 8766, `--no-browser` —
  не открывать браузер). Тяжёлые операции (извлечение, сканирование, FTS, бенчмарк) идут
  фоновой задачей (`TaskManager`, одна за раз) с живым журналом; MCP-сервер запускается и
  останавливается из вкладки «MCP-сервер»;
- `src/confdb/bsl_parser.py` — разбиение модулей BSL на процедуры и функции;
  `rebuild_module` восстанавливает полный текст модуля из `module.body` и тел
  методов (нужен для проверки синтаксиса модуля из базы);
- `src/confdb/bsl_syntax.py` — проверка синтаксиса BSL собственным лексером и
  рекурсивным парсером (stdlib, без платформы и Java): все режимы лексера
  (точка-член, `Асинх`/`Ждать`, `&`-директивы и аннотации, препроцессор,
  блоки `#Удаление`, многострочные строки с `|`), баланс `#Если`/`#Область`,
  диагностики с позициями и кодами BSL Language Server. Основа инструмента
  `check_syntax`; приёмка — 41241 модуль трёх реальных конфигураций без
  ложных срабатываний. Грамматика — чек-лист ANTLR `BSLParser.g4`/`BSLLexer.g4`
  (1c-syntax/bsl-parser, LGPL-3.0), реализация собственная (см. `NOTICE.md`);
- `src/confdb/bsl_semantic.py` — необязательные семантические проверки
  (секция `check_syntax(semantic=True)`) поверх `bsl_syntax.analyze` и базы
  знаний. Ярус 2 (по базе, через область видимости метода — параметры, Перем,
  имена методов модуля, реквизиты/ТЧ объекта, цели присваиваний): вызовы
  несуществующих/не-Экспорт методов общих модулей (ERROR; в модулях форм
  WARNING — атрибут формы может затенять имя), обращения `Менеджер.Объект` к
  несуществующим объектам (цепочки с префиксом и `[индексом]` не проверяются —
  состав динамический), запросы внутри модуля через `query_lang` (синтаксис +
  таблицы/поля; шаблоны с `%`/`#`/`[` и усечённые тексты пропускаются), вызов
  серверного общего модуля из `&НаКлиенте`-метода (модули с «Вызов сервера» —
  легально). Ярус 1/3-лайт (без базы): неиспользуемые локальные переменные,
  `Прервать`/`Продолжить` вне цикла (ERROR), `Перейти`, устаревшие и
  небезопасные глобальные вызовы (`Вычислить`/`Выполнить`, ФС, интернет,
  модальные окна, `ТекущаяДата`/`Сообщить`/`Найти`) — только одноэлементные
  вызовы. Имена, не разрешённые ни во что известное, не помечаются никогда —
  граница анализа заявлена, а не угадана. Осознанно НЕ включены шумные
  проверки (неиспользуемые параметры — 96631 на УНФ, функция без Возврат,
  разрешение произвольных имён): для зависимостей кода есть
  `method_dependencies`;
- `src/confdb/bsl_analyzer.py` — лексический анализ BSL для `method_dependencies` и
  `method_result_schema`: маскирование строк и комментариев с пониманием многострочных
  литералов 1С с `|`, извлечение и проверка запросов через `query_lang`, разрешение общих
  модулей и метаданных, клиентский и серверный контекст. Синтаксис модулей он
  **не** проверяет — для этого есть отдельный парсер `bsl_syntax.py`
  (инструмент `check_syntax`);
- `src/confdb/header_props.py` — читает `meta_object.header_json` без повторной распаковки:
  версию конфигурации, синоним, режим совместимости и префикс расширения; коллекции
  измерений, ресурсов и реквизитов регистра с периодичностью и флагами режима записи;
  целевое пространство имён XDTO-пакета; подписки на событие (событие, обработчик,
  источники; `EVENTS_RU` — 20 пар en→ru, накопаны по 1723 подпискам четырёх cf-баз);
  состав плана обмена. Вид загруженного файла — по расширению
  `source.file`, а не по типу корневого объекта (`.erf` и `.epf` раскрываются в
  `ExternalDataProcessor`). Каждый читатель понимает ОБА формата заголовка:
  внутренний JSON декодера .cf и XML выгрузки (автоопределение по первому символу);
- `src/confdb/xdto.py` — разбор `XDTOPackage.bin` (обычный UTF-8 XML с BOM) в таблицы
  `xdto_*`; проверено на всех 334 пакетах тестовой конфигурации;
- `src/confdb/compare.py` — снимки объектов и сравнение двух баз (`compare_object`,
  `extension_diff`); тела методов и модулей сравниваются по sha1;
- `src/confdb/rights.py` — разбор файла прав роли `Role/<имя>/Role.0.c1brace` (объектные
  права, RLS по объектам, шаблоны RLS) для записи в базу; нераспознанный формат бросает
  `ValueError`, поэтому одна «чужая» роль не останавливает запись. Здесь же ОБЩИЙ для
  обоих конвейеров резолвер целей прав `TargetResolver`: по uuid цели (скобкофайл .cf,
  `resolve_uuid` — ленивая карта uuid→цель по четырём таблицам) и по точечному имени
  (`Rights.xml` выгрузки, `resolve`); соглашение единое — `target_object_id` реквизита,
  ТЧ и подобъекта есть объект-владелец, поэтому все права объекта выбираются одним
  условием. Словарь имён прав
  `RIGHT_NAMES` пересобран 2026-11-07 по подтверждённым источникам (uuid→eng —
  CSP-майнинг `dump/rights_map.py` по паре «выгрузка+cf» одной конфигурации,
  биекция 64↔64 с RLS-якорями; eng→rus — официальная справка 8.3 «ПравоДоступа»,
  таблица `RIGHTS_EN_RU`); права из `Rights.xml` выгрузки разбирает
  `dump/rights.py`;
- `src/confdb/bench.py` — бенчмарк железа, сохраняет лучшее число `workers` в
  `~/.confdb/config.json` (`src/confdb/config.py` — общий конфиг пользователя, его же
  читает TUI);
- `tests` — тесты на малых фикстурах (`test.bat`); `_tmp` — одноразовые пробники
  (игнорируются git).
